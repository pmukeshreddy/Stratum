# Buffalo root execution architecture

Buffalo's root action loop is its adaptive policy. The model receives the task, committed trajectory, tool/verifier results, child findings, selected harness state and remaining resources. It answers or calls `ipython(code)`, observes the result, and chooses its next action. There is no preliminary execution-mode inference, classification schema, decision injection or reconsideration API.

The pre-edit review separated the uncommitted work into two groups. The removed group comprised the strategy module, configuration, runtime mixin/call, Python/host reconsideration endpoints, classification examples, router events and label-based evaluation assertions. The retained group comprised kernel recovery, original task propagation, child admission/specification provenance, observation, state retrieval, bounded automatic refinement, complete-record evidence reduction, atomic state application, and execution accounting. No commit or whole-file diff was blindly reverted.

```text
Task → root model → answer or IPython action → evidence → next root model turn → final
                           └→ await rlm(...) → persistent asynchronous child
                                                    └→ findings → root's later context
```

`Runtime._run_turn` owns action execution and complete assistant/tool-block commits. `_invoke` starts/restores the session kernel, performs context management when needed, assembles current inputs and makes the ordinary agent request. Existing fixed/role-based provider routing chooses configured model identities; it does not inspect task IDs, prompt length or file counts to choose actions.

A final text response in the Python autonomous mode requests completion. Configured task verifiers can reject an incorrect result. Optional waiting for already admitted children, persistent goals and interactive yielding retain their existing lifecycle semantics. No completion rule requires any Python execution, child, recursion depth, message, evidence-use count, memory, skill or refinement edit.

The exact fresh-root foundation used for live validation is in [root-foundation.txt](root-foundation.txt). It is generated by `context.python_instructions`; selected subagent specifications and capability restrictions can change the relevant sections. The separate environment instructions and all original task messages remain in the full captured first request. Direct reasoning and direct completion are explicitly valid.

## Canonical recursive computation

The canonical Python implementation is `kernel_api.Recursive.__call__ → Recursive.run → Host.acall("rlm.run") → host_api.dispatch → Runtime.spawn_async → Runtime.spawn → Store.create`. `CodingAgents` inherits this implementation and adds candidate inspection/application only. The obsolete synchronous worker `rlm` override was removed. The older explicit-tool control plane's aliases now adapt to the same host admission implementation; they do not own another runtime.

Admission checks permissions, depth, child count and shared resources; resolves optional model/thinking overrides; applies an optional real subagent specification; and creates a stable child session. Shared admission returns directly. Isolated workspace preparation may take time before successful admission, but admission never waits for child model execution or its answer. The scheduler independently selects runnable sessions with global and task concurrency limits. Parent work can overlap child model calls and Python execution.

A child owns its context, kernel namespace, durable history and session identity. It inherits the effective model, reasoning, workspace policy, adapter, registered capabilities and resource limits. The immutable original task contract is available separately from the delegated assignment. Descendants call the same `rlm()` implementation within shared limits. Completion unloads a child kernel after checkpointing; a later parent message reactivates the same child and restores its state rather than creating another session.

`agent_message.send` routes through host dispatch to `Runtime.message` and `Store.send`. `Store.receive` commits messages to the recipient's context at a safe turn boundary. `_invoke` drains boundary messages again after asynchronous preparation/review/compaction and immediately before assembling the request. Findings arriving during those operations therefore reach the next model invocation; ordinary idle-only follow-ups keep their existing delivery policy. Completion messages contain actual child result text. `agent_observe.recent_messages` reads committed trajectory records through `Store.trajectory`; it excludes an unfinished assistant/tool block and can retrieve historical work after compaction/restart. Follow-ups preserve the same child ID, history and Python values.

Failures need no separate replanning operation. `_verify` appends the actual verifier result to normal context; Python/tool failures appear in committed results. Messages received after a candidate answer cause a further ordinary turn. The next root request can correct code, inspect more data, test again, start useful independent work, or finish.

## Exact Python surface and call semantics

All rows below describe runtime objects preloaded by `kernel_worker.Worker` and `kernel_api.bootstrap`, without imports or client construction. Host operations retain the session identity, permission envelope, action journal and resource accounting. An async call waits for its stated operation, not necessarily for the background work that operation starts. Host validation/permission failures cross the bridge as `RuntimeError`; Python signature/type checks can raise `TypeError` or `ValueError` before dispatch.

| `await compact()` | No arguments; `{'event_id': id_or_None}` | Compacts committed model context now, queues an automatic review checkpoint when appropriate, and retains Python state/history. Does not compact the currently executing unfinished block. |
| `await refine()` | No arguments; `{'request_id', 'status', 'event_id', 'trigger', 'waiting_for_resume'}` (terminal receipts also include a reason) | Admits a manual planning request and returns its receipt. Planning/application occurs at a safe boundary. Automatic review needs no call. Manual planning can propose nothing. |

Other generic preloads are `Path`, `pathlib`, `os`, `asyncio`, `json`, `session`, `context`, `history`, `artifacts`, `mcp`, `goal`, `verify`, `heartbeat`, `forget`, `remember_recipe`, and IPython's `get_ipython`. `shell` aliases `bash`. Coding sessions additionally preload `repo`, `git`, `edit`, `tests`, `build`, `lint`, `typecheck`, `bench`, `experiment`, and coding context/child helpers where admitted. These are capability surfaces, not an ordered workflow. Their live `help` and admitted schemas expose exact method arguments. Existing synchronous coding-capability result wrappers remain optionally awaitable; the canonical examples use their synchronous form. Plain harness/skill records do not use that compatibility behavior.

## Automatic refinement

`auto_refine` processes durable checkpoints for accumulated progress, execution/verifier failures, new child evidence, compaction and completion. Automatic reviews normally belong to the root; child trajectories and delivered findings are supplied there. Resource admission caps the whole pass and reserves time for an evidence/state-consuming action followed by completion. Its reserve is the larger of the configured floor and twice the slowest of the last eight root calls, with a 25% margin. Using the median of cheap inspection calls had underestimated synthesis latency in live validation. This resource estimate only admits optional refinement; it never selects root actions or requires a mechanism.

Progress reviews capture committed evidence and run in the background while ordinary root/child execution continues. A session has at most one such pass; overlapping checkpoints are coalesced. Plans retain their immutable baseline and wait for a safe application boundary, so an in-flight root invocation cannot see its context change. An active review does not gate completion. Shutdown settles its cancellation and usage; the evaluation path does this before saving accounting. Manual review remains explicitly awaited. Completion can still admit a bounded review when no pass is active and the allowance permits it.

The reviewer sees the complete original message contract plus real committed trajectory, existing state and earlier reviews. A strict false decision produces no planner or edit. A positive decision supplies guidance to the planner; large evidence is reduced in complete records with source identities and the unreduced task contract. The host validates supplied event IDs, scope, skill code, versions and baseline conflicts. The batch applies atomically at a safe boundary. New versions are selected for later retrieval. When configured, a completion-time applied change creates a normal follow-up turn; a decline leaves completion valid. No edit quota exists.

Manual `refine()` goes directly to evidence-constrained planning. Compaction checkpoints, pending plans and interrupted requests retain their existing durable recovery semantics. Auxiliary requests have their own accounted request identities and do not replace trajectory call/return edges.

Context occupancy uses reported provider usage when prior input/output items are preserved in order, including when newly received child messages are inserted before a committed response. Every insertion is counted; rewritten/deleted items invalidate the estimate. Preemptive compaction can defer near the wall deadline while the complete context still fits. Hard capacity and forced compaction remain enforced. Shell completion is delivered once through an awaited result; unawaited processes retain their asynchronous notification. These changes and their timing evidence are described in [latency-validation.md](latency-validation.md).
